# Work backward from delivery

Use actual remaining time. A suggested 180-minute allocation is 0–10 constraints/environment, 10–30 first slice, 30–110 required features, 110–150 edge/integration checks, 150–170 scope freeze and verification, and 170–180 delivery buffer. These are adjustable planning suggestions, not assessment rules or mandatory phases. Set checkpoints using available clock tools rather than claiming background monitoring.

If fewer than 30 minutes remain, stop optional features, lock scope, repair the core path, and prepare delivery. If fewer than 10 remain, prioritize startup, the required acceptance demonstration, saved files, and the permitted submission procedure. Preserve security boundaries; state incomplete behavior.

Before delivery, verify the documented start command from a clean or fresh session when practical; exercise the main path and important failure; check changed files for secrets and accidental artifacts; and map required outputs to evidence. Include setup, exact run/check commands, known limits, and what remains untested. Submit only when requested and allowed; verify the resulting destination. Do not assist a separate AI-prohibited written or interview stage.

For a provided browser IDE, use its actual assigned port and bind the development server to `0.0.0.0` when required. Keep the serving terminal alive and confirm the embedded preview. Do not add tunnels or external hosting. Keep processes bounded; stop unused servers before starting another. Follow the displayed hard end time and actual task instructions over example timing. Do not open a limited-use practice attempt without explicit authorization.

Under a Computer Use ban, preview confirmation is performed manually by the participant. Provide concrete steps: open the built-in preview, enter the acceptance input, perform the main action, compare visible output with the expected result, and check the important error state. Do not drive a browser, desktop, screenshot agent, or automation tool to perform these steps. Report CLI checks separately from participant-confirmed UI evidence; do not infer UI success from an HTTP success alone.
