# 주문 재시도 안정화 — 실제 수행 기록

이 작업은 로컬 합성 연습이다. 실제 시험·공식 starter를 발견하거나 검증했다는 의미가 아니다. 외부 네트워크/모델/브라우저/다른 에이전트를 사용하지 않았다.

## 확인 순서와 첫 실행

1. 첫 셸 실행: 프로젝트에서 `pwd && rg --files ...`로 README, AGENTS, package, 주문·결제·테스트 파일 이름을 확인했다.
2. `cat AGENTS.md README.md package.json && rg --files`로 범위, API 계약, 실행 명령을 읽었다.
3. `.agents/skills/*/SKILL.md`의 이름/설명 frontmatter만 확인해 `ship-small`을 선택했다.
4. 선택한 스킬 본문 → `src/orders.ts` → `src/payments.ts` → `src/server.ts` → 기존 테스트 순서로 읽었다.
5. `STAKEHOLDER.md`와 필요한 risk/data/debug 참고를 읽고 첫 앱 실행 검증인 `npm test`를 수행했다: 기존 테스트 1/1 통과. 별도 환경 스킬이나 외부 자료는 읽지 않았다.
6. 수정 전 Node CLI 재현: 같은 키의 두 요청이 서로 다른 주문 ID를 반환했고, `tok_timeout_after`가 `failed`를 반환했다. 기존 성공 테스트만으로는 결함을 잡지 못했다.
7. 수정 전에 사용자에게 최소 계획(요청 정규화, 원자적 주문 예약, 결제 조회/재조정)을 알렸다. 마지막에 finish 참고를 읽고 실제 `npm start` 실행도 확인했다.

## 필요한 변경과 근거

- `src/orders.ts`: 검증된 기존 필드만 정해진 순서로 직렬화한다. 최상위/항목의 무시되는 추가 필드와 객체 필드 순서는 동일성을 바꾸지 않는다. 배열 순서와 실제 값은 유지한다.
- `BEGIN IMMEDIATE` 안에서 키 조회/비교/주문 삽입을 완료한다. 모든 서비스 인스턴스와 프로세스가 같은 SQLite 파일을 이용하면 동시 예약이 직렬화된다. 결제 `await` 동안 DB 트랜잭션을 유지하지 않는다. 기존 테이블을 유지하고 키 조회 인덱스만 추가했다.
- 동일 키/동일 값은 기존 ID로 201, 다른 수락 값은 기존 오류 객체 형태의 409를 반환한다. 키 없는 요청은 각자 새 주문을 만든다. 기존 응답 필드, GET/health, STARTER_MARKER, 결제 어댑터는 변경하지 않았다.
- 주문 ID를 결제의 안정 키로 계속 사용한다. pending 재시도는 먼저 게이트웨이를 조회하며 `not_found`일 때만 같은 키로 결제를 시도한다. 승인/거절은 paid/failed, 예외 후에도 조회 결과가 없으면 pending이다. 최종 상태를 동시 요청의 오래된 관측으로 덮어쓰지 않는다.
- 새 패키지, 서비스, API, 백그라운드 작업은 추가하지 않았다.

## 명령과 결과

- 수정 전 `npm test`: 1/1 통과. 위 CLI 재현에서는 중복 및 잘못된 실패 상태 확인.
- 회귀 테스트 추가 후 첫 `npm test`: 11/12 통과. SQLite 행이 null prototype인 점 때문에 객체 전체 비교 테스트가 실패했다. 구현 문제가 아닌 검증 표현을 실제 `count === 1` 비교로 수정했다.
- HTTP 테스트 추가 후 `npm test`: **13/13 통과**, 실패 0. 기존 응답, 정규화 재생, 충돌, 키 없는 독립 주문, 총액 0, 잘못된 입력/키 미소비, 결제 거절, 승인 전·후 타임아웃, GET, 재시작을 확인했다. 서비스 두 개의 12개 동시 요청과 별도 프로세스 6개의 요청에서 주문 1개/승인 결제 1개를 DB 조회로 확인했다.
- `tests/http.test.ts`는 실제 서버 프로세스를 실행하고 루프백 HTTP로 health/create/replay/conflict/get/404/400/잘못된 JSON/결제 실패·복구를 검증한다.
- `PORT=18087 DATA_DIR=./.smoke-data npm start` 후 별도 Node HTTP CLI: `health, paid replay, decline, pending recovery PASS`.
- 스모크 정리에서 Ctrl-C가 npm 자식 서버를 남겼다. 상태 확인 뒤 해당 `node src/server.ts` PID에 SIGTERM을 보내 종료했고, 포트 연결 실패 확인 후 일회성 DB를 삭제했다. 중간 `/proc/<pid>/cwd` 확인은 EACCES로 실패했으나, 프로세스 목록으로 확인한 PID의 종료와 정리는 성공했다.
- 저장소에는 starter 파일이 모두 untracked라 `git diff`로 기준본 대비 차이를 얻을 수 없었다. 실제 변경 산출물은 orders 구현, 기존 테스트 확장, 새 HTTP 테스트, 이 기록이다.

## 범위와 남은 제한

- 로컬 Node 24/SQLite와 제공된 가짜 결제 계약에서 검증했다. PostgreSQL·실제 결제망·브라우저 검증은 수행하지 않았다.
- 결제 완료 직후 프로세스가 중단되는 창은 pending 주문 + 독립 게이트웨이 승인 기록으로 구성해 검증했다. 실제 OS 강제 종료 시점 주입이나 전원 장애 테스트는 하지 않았다. 재시작 자체와 별도 프로세스 동시 요청은 실제로 실행했다.
- 복구는 같은 키 POST 재시도 시 수행한다. GET은 저장된 상태를 반환하며 자동 폴링/백그라운드 복구는 없다.
- 과거 버전이 이미 만든 중복 주문/결제나 잘못된 terminal 상태는 자동 삭제·환불·일괄 수정하지 않는다. 기존 동일 키 중복 행이 있으면 첫 행을 재사용한다. 이미 생긴 중복 거래의 정리는 별도 업무 판단이 필요하다.
- DB를 직접 쓰는 다른 코드까지 강제하는 UNIQUE 제약은 추가하지 않았다. 이 서비스의 모든 생성 경로는 SQLite 쓰기 트랜잭션을 통과한다. 장시간 외부 DB 잠금, 디스크 장애, 저장소 직접 변조는 이번 검증 범위 밖이다.
- 남은 실행 차단 요인은 없다. 실행: `npm start`, 자동 검증: `npm test`.
